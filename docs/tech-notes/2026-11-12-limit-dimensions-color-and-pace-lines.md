# 限额维度分类 · 状态三色 · 平均消耗参考线 — 设计笔记

> 日期：2026-11-12
> 版本：v1.4.0 引入
> 状态：已实机验证（用户逐个平台核对：百度 / 火山 / 智谱 / 谷歌 / MiniMax 均通过；Kimi 周维度未接入）

---

## 0. 这轮要解决什么

用户提出三类诉求：

1. **各平台的限额规则不同**，不能用同一套 UI 展示（有的只有 5h，有的 5h+7d，有的是包月）
2. **状态颜色语义要收敛**：红=耗尽不可用 / 橙=超阈值还能用 / 绿=安全
3. **7 天限额也要有「平均消耗」参考线**（参考千帆月进度条的算法）

---

## 1. 限额维度分类（先分类，再决定 UI 挂哪个窗口）

分类结果直接落在数据层 —— 「这个平台有没有周窗口」由 Provider 决定，
UI 层只认 `ProviderQuota.weeklyWindow` 有没有值，不认平台身份。

| 平台 | 5h 主窗口 | 7 天窗口 | 依据 |
|------|-----------|----------|------|
| MiniMax | 有 | **无**（订阅每周 unlimited） | `weeklyWindow = nil` |
| 智谱 GLM | 有 | **有** | `TOKENS_LIMIT` + `unit=6`，`percentage` 即已用% |
| 火山引擎 | 有 | 有 | `AFPWeekly`（GetAFPUsage）/ `Level=weekly`（降级路径） |
| Gemini | 有 | 有 | 网页 `weekly-usage` 区块 |
| 百度千帆 | 月窗口 | 无（包月维度） | 单窗口 `displayName="月"` |
| Kimi | 有 | 无（结构未确认，见 §5） | `weeklyWindow = nil` |

**关键设计**：分类做在 **Provider 层**而不是 UI 层。
UI 侧只需 `if let weekly = quota?.weeklyWindow`，就自动实现了「有的显示有的不显示」。
若在 UI 层按平台枚举判断，以后每加一个平台都要改 UI 分支 —— 是典型的「配置项数据流通断在中间」。

## 2. 状态颜色三色化

原四色（`SemanticColors.color(for:)`）：

```
<75 绿 │ 75-90 黄 │ 90-99 橙 │ >=99 红
```

问题：黄色与橙色语义重叠（都是「注意」），红色却挂在 99% 上，
而用户真正关心的「完全用光、一分钟都用不了」应该是**剩余 0%**。

改为三色：

```
<75 绿（安全） │ 75-100 橙（超健康阈值，还能用） │ >=100 红（耗尽，不可用）
```

**改动范围刻意收窄**：`SemanticColors.color(for:)` 只被 popup 的两个视图引用
（`QuotaProgressBar` 填充色 + `ProviderCardView` 标题数字色），
菜单栏走的是独立的 `MenuBarController.nsColor(for:settings:)`（读 SettingsStore 阈值），
两者互不影响。因此这次三色化**只影响下拉菜单**，不会牵动通知/状态栏那套三级告警体系。

⚠️ 遗留的已知不一致：popup 的橙线是硬编码 75%，而菜单栏读的是可配置阈值（默认也是 75）。
用户在设置面板拖阈值后，popup 不跟随。若要联动，需把 `warningThreshold` 沿
PopupView → ProviderCardView → QuotaProgressBar 传下去。

## 3. 平均消耗参考线

用户定义的语义：**「按当前时间点，平均速度消耗的话应该用到多少百分比」**。
实际用量超过这根线 = 用得太快 = 警告。

千帆是自然月（天数 28~31 不定），7 天窗口是固定 7 天，所以两种周期算法：

| 维度 | 周期起点 | 实现 |
|------|----------|------|
| 千帆月窗口 | `resetAt` 往前推**一个自然月**（`Calendar` `.month = -1`） | `BaiduUsageParser.expectedPercent(resetAt:now:)` |
| 各平台 7 天 | `resetAt` 往前推**固定 604800 秒** | `QuotaWindow.expectedPercentByElapsedPeriod(periodSeconds:now:)` |

统一公式：

```
expected% = clamp((now − periodStart) / (resetAt − periodStart) × 100, 0, 100)
```

**千帆为什么不能用固定 30 天**：自然月有 28/29/30/31 天，固定 30 天会让参考线
在 2 月系统性偏移（周期起点算错），月底那几天线会跑到 100% 以外。

**参考线随时间前移的实现**：`expectedPercent` 是纯函数，每次 UI 渲染时用 `Date()` 重算。
刷新周期内参考线几乎不动（7 天窗口一天才走 14%），所以不需要每秒刷新卡片。

### 颜色与参考线的耦合

进度条在两种模式间切换配色：

| 模式 | 判据 | 绿 | 橙 | 红 |
|------|------|----|----|----|
| 有参考线（月 / 7d） | `used` vs 竖线位置 | 未超线 | 超线 | `used >= 100` 耗尽 |
| 无参考线（5h 主窗口） | `used` vs 75% 固定阈值 | < 75% | 75~100% | `>= 100%` |

即：**红色是绝对的「耗尽」，橙色是「相对参考线/阈值的超支」**。
参考线只是把橙色的触发条件从固定值换成了动态值，颜色语义本身不变。

## 4. 顺带修掉的「蓝色进度条」

7 天进度条原先是 `ProgressView(value:total:).progressViewStyle(.linear)` ——
SwiftUI 默认渲染成**蓝色**，与「红/橙/绿状态语义」完全无关，
用户看到蓝色进度条自然读不出任何告警信息。现在统一换成 `QuotaProgressBar`。
